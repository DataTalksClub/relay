Send a test email: quickstart

  1. Prepare your client. Open Clients, configure sender addresses, create an active API key, and prepare an active transactional template with sample variables. Use the setup checklist on the client page.
  2. Check the message without sending. Use your own client key and template; replace the example recipient and context with values required by that template. The URL below is the configured sandbox base URL.
Validate and render — no email is sent
export DATAMAILER_URL="{{ docs_base_url }}"
export DATAMAILER_API_KEY="YOUR_CLIENT_API_KEY"
curl -sS "$DATAMAILER_URL/api/transactional/send" \
  -H "Authorization: Bearer $DATAMAILER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","template_key":"YOUR_TEMPLATE_KEY","context":{},"dry_run":true}'

The dry-run response includes the rendered content, with no persisted or queued message. Validation errors identify missing variables or invalid sender policy. A successful dry run does not verify delivery.

  1. Send to an address you control. Review the content, then repeat the request with dry_run:false and a unique idempotency_key. This step sends an actual email.
  2. Check the outcome. Save the returned message ID and query GET /api/transactional/messages/{message_id}, or open Email activity with the same client selected. Queued and sent to provider are separate from delivered. A delivery event does not prove inbox placement.

Authentication and troubleshooting

Client requests use Authorization: Bearer $DATAMAILER_API_KEY. Each key belongs to one client. Relay management uses separate admin API keys and explicitly scoped /api/admin/clients/{client_id}/ routes.

For invalid credentials, check client access and key revocation in settings. For validation errors, inspect the returned field details. Retry transient errors with the same idempotency key.
